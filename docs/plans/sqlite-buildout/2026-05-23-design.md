# SQLite buildout — design

**Date:** 2026-05-23
**Branch:** `feat/sqlite-buildout` (off `origin/main` @ [`fa1173b`](https://github.com/nelson2005/numbox/commit/fa1173b))
**Target:** fork PR (`nelson2005/numbox`) → upstream PR (`Goykhman/numbox`)

## Summary

Expand `numbox/core/bindings/_sqlite*.py` from its current 3-function shell (`sqlite3_open` / `sqlite3_close` / `sqlite3_libversion`) to a 60-function low-level surface (57 new + 3 retained) that covers the standard prepare → bind → step → column → finalize lifecycle plus BLOB incremental I/O, all six modern callback-hook APIs, and version-sensitive 64-bit row-count accessors. Ethos matches the just-landed [libc bindings expansion](https://github.com/Goykhman/numbox/pull/12) (PR #12 / 0.5.12): thin `@proxy` wrappers around `_call_lib_func`, no opinionated lifecycle abstractions, no high-level helpers. Windows support is in-PR via a new generic `_windows_bundled_dll_path` fallback in `load_lib`.

## 1. Architecture & file layout

The buildout reuses the established bindings infrastructure verbatim. No new architectural primitives — every wrapper is `@proxy(signatures.get("name"), jit_options={"cache": True})` around `_call_lib_func("name", (args,))`, or `@proxy_if_available(sqlite3_lib, signatures.get("name"), jit_options={"cache": True})` for version/compile-flag-sensitive functions.

## 3. Cross-cutting design choices

### 3.1 Windows lib loader

Current `load_lib`'s Windows branch calls `find_library(name)` for anything other than `c`/`m`. On a fresh Python install, `find_library("sqlite3")` returns `None` because `sqlite3.dll` lives at `<sys.base_prefix>/DLLs/sqlite3.dll` — bundled with CPython, but not on `PATH`. Conda Python uses `<base_prefix>/Library/bin/sqlite3.dll` instead.

Add a generic fallback (not SQLite-specific) to `numbox/core/bindings/utils.py`:

```python
def _windows_bundled_dll_path(name):
    """Best-effort: find a DLL bundled with the Python distribution on Windows.
    Tries <sys.prefix>/DLLs (CPython), <sys.base_prefix>/DLLs (venv → base),
    and <sys.base_prefix>/Library/bin (conda)."""
    import os, sys
    dirs = [
        os.path.join(sys.prefix, "DLLs"),
        os.path.join(sys.base_prefix, "DLLs"),
        os.path.join(sys.base_prefix, "Library", "bin"),
    ]
    for d in dirs:
        candidate = os.path.join(d, f"{name}.dll")
        if os.path.exists(candidate):
            return candidate
    return None
```

`.pyd` is not tried — `_sqlite3.pyd` is Python's wrapper extension (exports `PyInit__sqlite3`, not the raw `sqlite3_*` C surface) and CDLL-loading it does not expose what we need.

### 3.2 `load_lib_with_handle` refactor

`@proxy_if_available(lib, sig, ...)` needs a CDLL handle to query symbol presence via `hasattr(lib, func_name)`. The existing `load_lib(name)` discards the handle after registering symbols globally. Refactor `utils.py`:

```python
def _resolve_lib_path(name):
    """Pure path resolver. Returns absolute path or None.
    Same per-platform logic as load_lib, including the bundled-DLL fallback."""
    ...

def load_lib(name):
    """Register library globally; legacy contract (returns None)."""
    load_lib_with_handle(name)

def load_lib_with_handle(name):
    """Register globally AND return the CDLL handle for symbol-presence checks."""
    path = _resolve_lib_path(name)
    if path is None:
        raise RuntimeError(f"Could not find shared library for {name}")
    return load_lib_path(path)
```

In `_sqlite_conn.py` (the module-import entry for the suite):

```python
from numbox.core.bindings.utils import load_lib_with_handle
sqlite3_lib = load_lib_with_handle("sqlite3")
```

`sqlite3_lib` is then available for `@proxy_if_available(sqlite3_lib, sig, ...)` in any of the new `_sqlite_*.py` files via a local import.

### 3.3 Version-sensitive bindings via `proxy_if_available`

`numbox.core.proxy.proxy.proxy_if_available(lib, sig, jit_options=None)` checks `hasattr(lib, func.__name__)` at decoration time. If the symbol is present, you get a normal `@proxy`-wrapped dispatcher. If absent, you get a Python stub that raises `NotImplementedError` on call.

The stub does NOT expose `.as_func` — consumers passing a `proxy_if_available`-decorated binding as a function-typed arg must guard:

```python
if hasattr(sqlite3_changes64, "as_func"):
    use(sqlite3_changes64.as_func)
else:
    fall_back_to(sqlite3_changes)
```

Functions decorated with `@proxy_if_available` in this PR:

- `sqlite3_changes64` / `sqlite3_total_changes64` — added in SQLite 3.37 (Nov 2021); Python 3.10 ships SQLite 3.34
- `sqlite3_column_database_name` / `sqlite3_column_table_name` / `sqlite3_column_origin_name` — gated on `SQLITE_ENABLE_COLUMN_METADATA` compile-time option

### 3.4 Callback path for `sqlite3_exec` and the hook APIs

All seven callback-taking functions in this PR (`sqlite3_exec` + the six hooks) are bound as plain `intp`-for-callback. Caller produces a function pointer via `numba.cfunc`:

```python
from numba import cfunc, njit, types
from numbox.core.bindings import sqlite3_exec

@cfunc(types.int32(types.voidptr, types.int32, types.intp, types.intp))
def _row_callback(ctx, ncol, values_pp, names_pp):
    return 0  # nonzero → abort

@njit(cache=True)
def run_query(db_p, sql_p, cb_addr):
    return sqlite3_exec(db_p, sql_p, cb_addr, 0, 0)

rc = run_query(db_p, sql_p, _row_callback.address)
```

Three things to document in `CLAUDE.md` after this lands:

1. `@cfunc` must be created at Python-import time, not inside `@njit`.
2. Pass `cfunc_instance.address` as `intp` into the `@njit` function.
3. Pass `0` for no callback (matches C's `NULL`).
4. cfunc lifetime — for the hook APIs, the cfunc must outlive any registered hook. Easiest: keep the cfunc at module scope.

### 3.5 Out-param idiom

Already established by the existing `sqlite3_open(name_p, db_pp)` — the test allocates a `c_int64(0)` and passes `addressof(it)`. Same shape applies to `sqlite3_prepare_v2(db, sql, n, stmt_pp, tail_pp)` and `sqlite3_blob_open(..., blob_pp)`. From inside `@njit`, the canonical pattern is a `np.zeros(1, dtype=np.int64)` slot + `array_data_p(arr)`:

```python
@njit(cache=True)
def prepare_one(db_p, sql_p):
    stmt_holder = np.zeros(1, dtype=np.int64)
    tail_holder = np.zeros(1, dtype=np.int64)
    rc = sqlite3_prepare_v2(db_p, sql_p, -1,
                            array_data_p(stmt_holder),
                            array_data_p(tail_holder))
    return rc, stmt_holder[0]
```

No new helper. Documented in `CLAUDE.md` alongside the existing `lowlevel.py` primitives.

### 3.6 Constants module + public surface

`_sqlite_constants.py` is `from`-star-imported by `numbox/core/bindings/__init__.py`, matching the established "anything not `_`-prefixed is public" rule. The upper-case `SQLITE_*` names won't collide with the lower-case C-function-named wrappers.

### 3.7 Lifetime gotchas — documented in `CLAUDE.md`, no code constraints

- **`bind_text`/`bind_blob` destructor.** Pass `SQLITE_TRANSIENT` (= -1) by default — SQLite copies the buffer. `SQLITE_STATIC` (= 0) means SQLite assumes the buffer outlives the statement; only safe when the caller can guarantee that.
- **`sqlite3_errmsg` lifetime.** The returned `const char*` is owned by SQLite and valid until the next API call on the same connection. Read it via `get_str_from_p_as_int(errmsg_p)` immediately, before any other call on `db`.
- **`sqlite3_expanded_sql` cleanup.** Returns a `char*` the caller MUST free with `sqlite3_free()`. Hence both functions live in `_sqlite_exec.py`.
- **Callback (`@cfunc`) lifetime for hooks.** Hooks store the callback pointer until cleared. The cfunc instance must outlive the hook registration; if it goes out of scope while a hook references it, calls into freed memory follow.

### 4.8 Cross-cutting

- **Windows.** Zero Windows-specific tests; once `load_lib_with_handle("sqlite3")` resolves via the bundled-DLL fallback, the 58 bindings behave identically across platforms. The matrix CI exercises every test on `windows-latest` Python 3.10-3.14. The libc `getenv` MSVCRT/UCRT split has no SQLite analog because SQLite doesn't read process state through CRT-managed structures.
- **No new `auxiliary_utils.py` helpers.** Existing `str_from_p_as_int` (Python-side, ctypes) and `get_str_from_p_as_int` (njit-side, from `utils/lowlevel.py`) cover all string-decode needs.
- **`collect_and_run_tests(__name__)`** at the bottom of each test file so `python test/core/test_sqlite_*.py` runs them directly.
- **Total new tests:** ~55.

### 5.3 CI expectations

The fork matrix (`numbox_ci.yml`) runs every test on Python 3.10-3.14 × ubuntu / ubuntu-arm / windows / macOS × min/max numba. All ~55 new tests must pass on all rows. Specifically:

- **Windows rows** exercise the new `_windows_bundled_dll_path` fallback (the most likely failure point)
- **All Python versions** ship SQLite ≥ 3.34.0 (3.10's floor); every always-bound function here is from SQLite ≤ 3.14.0; the two `_64`-suffixed accessors require 3.37+ and are gated by `proxy_if_available`
- **macOS** uses the system `libsqlite3.dylib` (in `/usr/lib/`)
- **flake8** at `--max-line-length=127` (numbox project default — note: 127, not the cross-project 120)

## 6. Out of scope

Explicit callouts to prevent reviewer confusion. None of these are in this PR.

- **Structref wrappers** for `sqlite3*` / `sqlite3_stmt*` (a `Connection` / `Statement` structref API). Low-level parity ethos. If a downstream consumer wants ergonomics, that's a separate design.
- **High-level helpers** like `fetchall_to_array`, `exec_to_dataframe`, etc.
- **User-defined SQL functions** — `sqlite3_create_function_v2` + the `sqlite3_value_*` / `sqlite3_result_*` API surface. This is its own significant buildout (analogous to numbduck's UDF/UDAF work); explicitly deferred.
- **Backup API** (`sqlite3_backup_init` / `_step` / `_finish` / `_pagecount` / `_remaining`)
- **Serialize / deserialize** (`sqlite3_serialize` / `sqlite3_deserialize`)
- **Load extension** (`sqlite3_load_extension` / `sqlite3_enable_load_extension`)
- **Config** (`sqlite3_config` / `sqlite3_db_config`)
- **Virtual table interface** (the entire `sqlite3_module` / `sqlite3_create_module` API)
- **Legacy tracing** — `sqlite3_trace` and `sqlite3_profile` are deprecated; superseded by `trace_v2` (already in scope)
- **`sqlite3_get_table` / `sqlite3_free_table`** — deprecated convenience

## 7. Follow-ups

Add to `CLAUDE.md` "Follow-ups" (after the existing Vector/List entry):

- User-defined SQL functions: `sqlite3_create_function_v2` + the value/result API. Large enough for its own design; relevant for numbduck-style consumers but separate scope from low-level bindings.
- Backup API. Useful for streaming `:memory:` → file or file → file workflows; six functions plus progress callback.
- `sqlite3_serialize` / `sqlite3_deserialize` for in-memory snapshots.
- Higher-level structref wrappers if a downstream consumer (numbduck-like, or a new project) needs ergonomic Connection / Statement types.
- When Python 3.10 drops out of the support matrix: drop the `proxy_if_available` gate on `changes64` / `total_changes64`.
